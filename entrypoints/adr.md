# ftd-adr

```text
/ftd --adr <file|folder> [--run <run-id>] [--output-dir <dir>] [--base-adr <adr-id|none>]
/ftd-adr <file|folder> ...                      # the same command
```

Intent: keep an already validated Test Case suite current as ADRs and other project decisions arrive — **without regenerating the suite and without rereading the original sources**. Natural language ("analyze the new ADRs", "update the tests from this ADR folder") reaches it through the host's `resolved_intent="ftd-adr"`; `scripts/workflow.py` holds no phrase list.

- **Baseline:** `--run` wins; otherwise the current validated run of the artifact root (`.ftd/current-run.json`, verified: VALIDATED, intact manifest, matching canonical digest). A run is never picked by folder name or time. On top of it, the latest **finalized** ADR round of that run (`.ftd/current-adr.json`, one entry per canonical run, verified on use) — or `--base-adr` (an earlier round, or `none` for the canonical suite). Corrupt or mismatching ADR state fails closed; it never silently falls back to the canonical suite. `current-run.json` keeps meaning the current validated canonical run.
- **Command:** `scripts/workflow.py adr <phase>` (same as `scripts/adr.py <phase>`):
  1. `start --scope <file|folder>` inventories the selection and writes `<run>/adr/<adr-id>/work-order.json` (`adr-001`, `adr-002`, … never reused).
  2. You write the analysis; `submit-analysis --adr-id <id> --file analysis.json`.
  3. You write a complete procedure for every UPDATE / CREATE; `submit-procedures --adr-id <id> --file procedures.json`.
  4. `finalize --adr-id <id>`.
  - `lookup --adr-id <id> --source <parent source> --query "..."` (or `--lines A-B`, at most 80 lines) returns a bounded excerpt of an original project source from the parent run's persisted evidence; each lookup is counted.
  - Lifecycle `STARTED → ANALYZED → PROCEDURES_READY → FINALIZED`. A rejected submission returns every problem at once and records nothing. A finalized round is immutable: a mistake is fixed by a new round.
- **Incremental reading:** every physical file of the selection (a folder is recursive only below itself) gets a disposition: `NEW_READ`, `CHANGED_READ` (text extracted with the same readers as `/ftd-gen`: `.md`, `.txt`, `.pdf`, …), `UNCHANGED_REUSED` (same digest as an analyzed file: its statements and decisions are reused, its text is not reread), `UNSUPPORTED`, `FAILED`. A file that disappears is `SOURCE_REMOVED_FROM_SELECTION`: deleting a file is not a business decision, so its decisions stay in effect until a decision explicitly revokes or supersedes them. Original project sources are never reread (`runtime_full_parent_source_rereads = 0`).

## The analysis (you)

The selection is a **change corpus**: formal ADRs, approved customer decisions, meeting notes, transcriptions, drafts, standards, proposals, rejected or future ideas, implementation and operational observations — mixed, and usually without naming any requirement, rule or Test Case. Relationships are found by meaning, never by matching identifiers or words. Work from the work order only (persisted parent state: requirements, claims, domain model, Test Cases, Questions, Findings, organization).

- `sources`: every NEW_READ / CHANGED_READ file reviewed once — `document_status` (`APPROVED_DECISION`, `DRAFT_DECISION`, `SUPPORTING_CONTEXT`, `REFERENCE_STANDARD`, `SUPERSEDED_DOCUMENT`, `UNKNOWN_STATUS`, `MIXED_CONTENT`, `NO_MATERIAL_CONTENT`) and a `summary`. A file's status is not the authority of each statement in it.
- `statements` — the ADR evidence catalog: each material statement with `source`, `reference`, a **verbatim** `excerpt`, `kind` (DECISION, OBSERVATION, REQUIREMENT_CHANGE, BUSINESS_RULE, CONSTRAINT, ASSUMPTION, OPEN_QUESTION, RISK, MIGRATION_CONCERN, IMPLEMENTATION_FACT, OPERATIONAL_FACT, INTEGRATION_CHANGE, ACTOR_OR_PERMISSION_CHANGE, STATE_OR_WORKFLOW_CHANGE, DATA_CHANGE, PHYSICAL_OR_DEVICE_CHANGE, NON_FUNCTIONAL_CHANGE, PROPOSAL, DRAFT_IDEA, REJECTED_IDEA, FUTURE_IDEA, REFERENCE_INFORMATION), its own `status` (`APPROVED` only with an `authority_evidence` quote of the same file that shows the approval; else DRAFT, PROPOSED, REJECTED, FUTURE, OBSERVED, UNCERTAIN, REFERENCE), `meaning`, `concepts`, `candidate_concepts`, `confidence`, and a `disposition`: DECISION, QUESTION, FINDING, CONTEXT or NO_TEST_IMPACT (the last two with a reason). Irrelevant prose is not cataloged.
- `decisions` — effective changes built from statements, possibly across files (`statements: [...]`, provenance kept for every file). Their authority is **derived**: APPROVED only when a supporting statement is approved. `official_id` only when a source states it (otherwise the runtime mints `ADR-DEC-NNN`). `relationship` to the existing authority: CONFIRMS, CLARIFIES, ADDS_BEHAVIOR, CHANGES, SUPERSEDES, REMOVES_BEHAVIOR, CONFLICTS_WITH, NO_TEST_IMPACT, UNCLEAR, ALREADY_INCORPORATED, REVOKES_DECISION. CHANGES / SUPERSEDES / REMOVES_BEHAVIOR / CONFLICTS_WITH name the `previous_authority` (requirements or earlier decisions, and the previous rule's statement, which stays visible). Disagreeing statements are never voted on: an approved statement may override non-approved ones (`authority_resolution`), otherwise raise a Question. An approved behavior change lists its testable `claims` and how each is covered: COVERED_BY_EXISTING, COVERED_BY_UPDATE, NEW_TEST, QUESTION, NOT_TESTABLE — this is how behavior no Test Case covers yet becomes a new Test Case. Analyze the hidden consequences too (authorization, negative paths, state transitions, audit, idempotency, concurrency, recovery, integrations, physical variants, E2E journeys, migration of existing data).
- `test_cases` — every affected Test Case: `test` (existing id) or `key` (new), `action` (AFFECTED_NO_CHANGE, UPDATE, CREATE, SUPERSEDE, REVIEW_ONLY, CONFLICT — what the ADR does to it; its execution status stays the FTD vocabulary), `impact` DIRECT / INDIRECT, `decisions`, `reason`. UPDATE / CREATE carry the complete resulting `design` (the same intent fields as canonical design: title, objective, family, actor, state, trigger, expected, failure_domain, priority, priority_reason, primary_type, basis, optional dimension); one independently diagnosable failure domain per Test Case. UPDATE / CREATE / SUPERSEDE need an APPROVED decision; drafts, supporting material and unclear authority give REVIEW_ONLY with a Question. A fundamentally different behavior is SUPERSEDE of the old case + CREATE of a successor (`supersedes`), never a deletion.
- `dimension_reviews` — targeted expansion, never global: for each approved behavior-changing decision, every expansion dimension once (NEGATIVE, BOUNDARY, OPERATOR_ERROR, MISUSE, STATE_TRANSITION, DECISION_TABLE, CONCURRENCY, RACE_CONDITION, IDEMPOTENCY, INTEGRATION, RECOVERY, CHAOS, SECURITY, AUTHORIZATION, DATA_INTEGRITY, CROSS_REQUIREMENT, E2E): MATERIALIZED, ALREADY_COVERED, QUESTION_REQUIRED or NOT_APPLICABLE with a reason. No case is manufactured to fill a dimension.
- `questions` / `findings` — linked to decisions, statements, requirements and affected Test Cases only (an unaffected Test Case is never changed). `question_dispositions` / `finding_dispositions` record RESOLVED_BY_ADR, PARTIALLY_ANSWERED_BY_ADR, STILL_OPEN / STILL_APPLIES, SUPERSEDED_BY_ADR for existing ones; history is never deleted.

## Procedures (you)

`{"procedures": [...]}` — one item per UPDATE / CREATE (`test`: its TC id or CREATE key), in exactly the canonical procedure format, validated by the **same** procedure gate as canonical Test Cases (preconditions, fixtures, one observable oracle per step, no abstract actions, no invented thresholds, unknowns, automation suitability / layer / tool hint, execution variants, request contract). ADR adds one stricter rule: a route, URL, selector or quoted message must appear in the ADR material, the parent's evidence or the case's previous definition. When the ADR says *what* changed but not *how* to execute it, keep the case, declare `MISSING_EXECUTION_SURFACE` / `UNKNOWN_SETUP_PATH` (linking the Question) and let it be NEEDS_REVIEW — never invent it.

## Finalize (runtime)

ADR-specific checks (the eight canonical gates are untouched): parent integrity, previous effective digest, complete source accounting, every decision dispositioned, every affected case traceable to ADR evidence, every UPDATE / CREATE complete, schema-valid and procedure-validated, unique ids and stable export keys, valid Question / Finding references, `unaffected_cases_changed = 0`, Azure delta limited to the intended cases. Ids continue the project numbering (an updated case keeps its id; a new one gets the next `TC-NNN`; Questions, Findings, requirements, coverage points and scenarios likewise). Then:

- `<run>/adr/<adr-id>/effective-suite.json` — parent suite + every finalized overlay up to this round, with a deterministic digest, lineage (parent canonical digest, previous round and digest, ADR source digests) and per-case history; untouched Test Cases are carried over byte-equal.
- `<artifact_root>/output/adr/<adr-id>/`: `adr-report.html` (offline; first screen answers the round, baseline, files read/reused, decisions, direct / indirect / updated / new / review / blocked / superseded / unaffected counts, Questions, Findings; then decisions → requirements → Test Cases → before/after → procedures → Questions / Findings), `adr-summary.md`, `adr-analysis.json`, `adr-decisions.json`, `affected-test-cases.json`, `proposed-test-cases.json`, `procedure-changes.json` (field-level before/after of the persisted definitions), `questions.json`, `findings.json`, `adr-manifest.json`, and `azure/azure-adr-export-package.json` + `azure-adr-preview.json`. Output locale: the parent run's.
- Only then is `.ftd/current-adr.json` moved, atomically. `/ftd --adr` makes no Azure call.

## Azure (explicit only)

The local delta holds only UPDATE / CREATE definitions. An existing case keeps its export key (`canonical:TC-042`), so publication updates the same Work Item; a new case gets `adr:TC-244`, stable across later rounds. Fields are the v2.4 fields (`FTD_METADATA_V1` unchanged, so an executor can ignore ADR metadata) plus an additive `FTD_ADR_METADATA_V1` block (round, action, decision refs, previous / effective definition digests, supersedes, source refs).

```text
/ftd-azure-publish --prepare --adr <adr-id> --organization ... --project ... --plan ... --auth azure-cli
/ftd-azure-publish --apply <output>/adr/<adr-id>/azure/publication-plan.json --auth azure-cli
```

Prepare is read-only. Beyond the normal checks (explicit target, remote revision → CONFLICT, no overwrite of unmanaged items, no delete) it requires the Work Item to carry its `ftd-key`, and reads the execution history of each affected existing Test Case only: a semantic change to an executed Test Case — or one whose history cannot be read (`EXECUTION_HISTORY_UNKNOWN`) — is `REVIEW_REQUIRED`, not UPDATE, until the human decides: update the same Test Case (`--review TC-042=UPDATE_SAME_TEST_CASE`) or create a successor in a new ADR round. Supersession is a proposal, never a write. Apply re-verifies the package, effective and canonical digests, target and revisions, and writes only after approval. Test Runs, results, attachments and execution evidence are only ever read; the publisher's write surface remains the four Test Case / Suite operations. After an ADR publication, a normal canonical prepare reports those Test Cases as `MANAGED_BY_ADR_LINEAGE` instead of reverting them.
